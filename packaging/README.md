# Notification access and MSIX

WinNotch uses the Windows User Notification Listener. Previews are off by default. In Settings, select **Allow access**, respond to the Windows permission prompt yourself, enable **Preview new Windows notifications**, and save. Denying access leaves all other modules usable. Revocation stops reading and clears the last preview on the next two-second check. To resume after changing Windows privacy settings, use **Allow access** again.

Desktop listener availability varies by Windows build. If the portable app cannot request/read notifications, use an MSIX installation with the `userNotificationListener` capability declared in `AppxManifest.xml`. The source includes this manifest and a packaging script. The listener polls every two seconds only while enabled and authorized; old notifications are never replayed on startup. Content is local and transient. Dismiss clears only WinNotch's last preview, never the Windows original.

Build the portable executable first, then `./package.ps1` using a Windows SDK installation. This produces **an unsigned MSIX**, validates the manifest, and does not install anything. For an installable package, sign it with a code-signing certificate whose subject matches the manifest publisher (`CN=WinNotch Preview`): `./package.ps1 -SigningCertificateThumbprint <thumbprint>`. The certificate must be available in the current user's personal certificate store. Use your normal trusted signing/distribution process. A local test certificate requires explicit trust on the test machine; this script does not create or trust certificates, change Developer Mode, or install packages.

On 4 October 2026, the user granted access to the portable build on the test laptop. WinNotch reported **Listening locally**, received a real Windows PowerShell test toast, and displayed its source/title/body in Alerts. The original toast remained in Windows history after the transient peek ended. **MSIX was not needed on that machine.** This does not establish support on all Windows configurations; the deny/revoke paths and the MSIX permission flow still need manual testing. Packaged startup registration also needs validation; prefer the portable build for current sign-in startup support.

References: [Notification listener and permission](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener), [MakeAppx packaging](https://learn.microsoft.com/en-us/windows/msix/package/create-app-package-with-makeappx-tool).
